# RPD — 台股強勢股預測與回測自動化系統

> Requirements & Product Design。本文件定義專案目標、範圍、需求與限制。
> 實作切分見 `MVP.md`，各 Phase 工作項見 `jobs.md`。

## 1. 一句話目標

在既有 `tw_market_core.py` 台股資料庫之上，建立一個**每日自動產出強勢股候選清單、
並能以歷史資料嚴謹回測該選股策略績效**的系統。

## 2. 背景與現況

- 既有資產：`tw_market_core.py`（約 2,427 行，本 repo 分支中不存在，位於使用者本機）。
  依描述具備：
  - 從 TWSE / TPEX 官方 API 抓取行情資料並建立資料庫。
  - 每日產出 Top20 成交量、Top20 成交值排行。
- 缺口：只有「資料」與「排行」，沒有「訊號 → 預測 → 驗證」的閉環。
  目前無法回答「照這個排行/訊號買，歷史上到底賺不賺錢」。

### 2.1 現況待驗證假設（Phase 0 必須逐項確認）

| # | 假設 | 驗證方式 |
|---|------|----------|
| A1 | 資料庫為 SQLite（或單機可查詢的 DB），含個股每日 OHLCV | 讀 schema |
| A2 | 覆蓋上市（TWSE）+ 上櫃（TPEX）全部普通股 | 抽樣比對官方清單 |
| A3 | 有可用的歷史回填深度（≥ 3 年為佳，≥ 1 年為底線） | 查最早日期與缺日 |
| A4 | Top20 排行有逐日留存（歷史可查），而非只有當日快照 | 查表 |
| A5 | 尚未納入三大法人買賣超、融資融券、除權息調整價 | 讀程式碼 |

假設不成立時，先在 Phase 0 補齊，再進入後續 Phase。

## 3. 既有方案盤點（preflight）

原則：資料層沿用自有系統；回測與模型不重造輪子，優先用成熟開源件。

| 方案 | 定位 | 採用決策 |
|------|------|----------|
| FinMind | 台股開源資料 API（法人、融資券、股利等） | **採用為補充資料源**：自有爬蟲缺的欄位優先接 FinMind，而非新寫爬蟲 |
| twstock | 台股基本抓取套件 | 不採用，功能被 `tw_market_core.py` 覆蓋 |
| FinLab / 量化平台 | 付費雲端策略平台 | 不採用（付費、黑盒、與自有資料庫整合差） |
| vectorbt | 向量化回測框架 | **候選採用**：每日換股型排名策略適合向量化；Phase 2 先做技術評估 |
| backtrader | 事件驅動回測框架 | 備選；事件驅動較慢、學習成本高，僅在 vectorbt 表達不了規則時考慮 |
| scikit-learn / LightGBM | ML 排序模型 | Phase 4 採用 LightGBM |

結論：**自建的只有「膠水」**——特徵計算、台股交易規則（漲跌幅/交易成本/處置股）、
排程與報表；回測核心與模型用開源件。

## 4. 使用者與情境

單一使用者（個人投資研究）。三個核心情境：

1. **每日盤後**：系統自動抓資料 → 算訊號 → 產出隔日強勢股候選清單（Top N + 分數 + 理由欄位）。
2. **策略研究**：修改訊號/參數後，一鍵對歷史區間回測，得到績效報告並與基準比較。
3. **事後追蹤**：系統自動記錄每日「當時發出的預測」，逐日對答案，累積 live 命中率，驗證回測沒有自欺。

## 5. 系統範圍

### 5.1 In scope

- **資料層**（沿用 + 擴充）：日 OHLCV、成交值/量排行；擴充三大法人、融資融券、還原權息價。
- **特徵/訊號層**：以日資料計算動能、量能、法人籌碼等特徵；規則式評分 →（後期）ML 排序。
- **預測層**：每日產出排名前 N 的強勢股候選清單，落地存檔（point-in-time 快照）。
- **回測層**：以歷史資料模擬「每日照清單換股」的報酬，含台股真實交易成本與漲跌停限制。
- **自動化層**：排程執行、失敗告警、日報輸出（檔案/訊息通知）。
- **追蹤層**：預測 vs 實際的滾動績效統計。

### 5.2 Out of scope（明確不做）

- 盤中即時行情、當沖、tick/分 K 級別資料。
- 自動下單（券商 API 串接）。產出僅供研究參考。
- 期貨、選擇權、權證、ETF 槓桿品。
- 基本面財報深度模型（僅可能用簡單過濾，如股本/產業）。
- 多使用者、Web 服務化。

## 6. 功能需求

| ID | 需求 | 優先級 |
|----|------|--------|
| F1 | 每日盤後自動更新資料庫（含補抓失敗重試、缺日偵測） | P0 |
| F2 | 特徵計算：動能（5/20/60 日報酬）、量能（量比、成交值排名變動）、波動、法人買賣超 | P0 |
| F3 | 規則式強勢股評分與 Top N 清單，逐日落地存檔 | P0 |
| F4 | 回測引擎：指定區間、持有天數、部位數、成本模型，輸出績效指標 | P0 |
| F5 | 績效報告：總報酬、年化、Sharpe、最大回撤、勝率、換手率、vs 基準（0050 或加權報酬指數） | P0 |
| F6 | 排程與告警：cron 驅動、失敗通知 | P1 |
| F7 | live 追蹤：每日預測對答案、滾動命中率報表 | P1 |
| F8 | ML 排序模型（LightGBM）+ walk-forward 驗證，與規則式基線比較 | P2 |
| F9 | 參數掃描/敏感度分析（避免過擬合單一參數） | P2 |

## 7. 非功能需求

- **Point-in-time 正確性（最高優先）**：任何日期 D 的訊號只能使用 D 收盤（含）以前可得的資料。
  回測與每日 live 產出必須走同一條程式路徑，杜絕前視偏差（lookahead bias）。
- **可重現**：同一資料庫 + 同一參數 → 逐 byte 相同的回測結果；隨機性（ML）固定 seed。
- **存活者偏差**：股票池以「當日存在且可交易」為準；下市股票資料保留，不得用今日清單回測過去。
- **官方 API 禮貌性**：遵守 TWSE/TPEX 速率限制（保守：每請求間隔 ≥ 3 秒），失敗退避重試。
- **效能**：全市場（~2,000 檔）单日特徵計算 < 5 分鐘；5 年回測 < 10 分鐘（向量化達成）。
- **單機優先**：SQLite + Python 腳本 + cron 即可，不引入服務框架。

## 8. 台股領域規則（回測正確性的硬約束）

回測引擎必須內建，否則績效數字無意義：

1. **交易成本**：手續費 0.1425%（買+賣各一次，可設折扣），證交稅 0.3%（賣出）。
   單趟來回成本約 0.585%（無折扣）——高換手策略會被成本吃光，必須如實計入。
2. **漲跌幅限制 ±10%**：訊號日收漲停的股票，隔日常常買不到或跳空；回測需支援
   「漲停不可買進、跌停不可賣出」的成交規則開關。
3. **成交價假設**：預設以「訊號日次一交易日開盤價」成交（訊號用收盤資料算，不可同日收盤成交）。
4. **流動性過濾**：排除日均成交值過低（如 < 5,000 萬）之個股；排除處置股、全額交割股（資料可得時）。
5. **除權息**：報酬計算需用還原價，否則除息日會被誤判為大跌。
6. **T+2 交割**：資金週轉模擬可簡化，但文件需註明簡化假設。
7. **基準**：預設 0050 buy-and-hold 與加權報酬指數（TAIEX Total Return）雙基準。

## 9. 成功指標

- **系統面（MVP 驗收）**：連續 10 個交易日全自動產出每日清單，零人工介入；
  回測與 live 路徑對同一天輸出相同清單。
- **研究面（不承諾獲利，承諾「可信」）**：回測報告能明確回答
  「策略扣除成本後是否勝過基準、風險（回撤）多大、對參數是否敏感」。
- **反指標**：若回測含前視偏差或漏計成本被抓到，視為 P0 缺陷。

## 10. 風險

| 風險 | 影響 | 對策 |
|------|------|------|
| 官方 API 改版/限流 | 資料中斷 | 抓取層隔離、FinMind 備援、缺日偵測告警 |
| 歷史深度不足 | 回測不可信 | Phase 0 先回填；深度 < 1 年不進 Phase 4 |
| 過擬合 | 回測漂亮、live 賠錢 | walk-forward、參數敏感度、live 追蹤對照 |
| 前視偏差 | 全部結論作廢 | 訊號/回測共用同一 point-in-time 資料介面 + 專門測試 |
| 個人專案時間碎片化 | 爛尾 | Phase 切小、每 Phase 有獨立可用產出（見 jobs.md） |

## 11. 名詞

- **強勢股**：本專案操作型定義＝「依訊號分數排名前 N，預期未來 H 日相對大盤有超額報酬」的個股；
  N、H 為策略參數（MVP 預設 N=10、H=5）。
- **Point-in-time**：只用當時已知資訊。
- **Walk-forward**：滾動式訓練/驗證切分，模擬真實逐期重訓。
